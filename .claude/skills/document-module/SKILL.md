# 레거시 모듈 문서화

## 원칙
- 분석 대상 폴더의 파일은 읽기만 한다. 수정 · 생성 · 삭제하지 않는다.
- 모든 주장에는 `파일:줄번호` 근거를 단다. 근거를 못 대면 규칙이 아니라 "미확인"으로 남긴다.

## 0. 인자 해석
- `$ARGUMENTS` 첫 값 = 모듈 경로, 나머지 = 범위 제한(예: "검색 화면만"). 범위가 있으면 그 밖은 다루지 않고 문서 머리말에 적는다.
- `<모듈명>` 은 폴더 이름이 아니라 아래 셋 중 하나다. 표에 없는 경로면 멈추고 묻는다.
  | 경로 | `<모듈명>` |
  |---|---|
  | `legacy/item-bank-php` | `item-bank` |
  | `legacy/assignment-thymeleaf` | `assignment` |
  | `legacy/grade-mssql` | `grade` |

## 절차 (순서대로. 각 단계 결과를 파일에 저장한 뒤 다음 단계로 넘어간다)
1. **계획 제시** — 파일 목록(`find <경로> -type f`)과 읽을 순서 · 단계별 산출 파일을 먼저 보여 주고 승인을 받는다.
2. **진입점** — URL · 컨트롤러 · 프로시저 등 외부에서 호출되는 지점을 목록화 → `docs/<모듈명>/ARCHITECTURE.md` 저장.
3. **의존 관계** — 누가 누구를 호출 · include 하는지(방향 포함), 공통 코드 · 외부 라이브러리 → 같은 `ARCHITECTURE.md` 에 추가 저장.
4. **데이터 흐름** — 테이블 · 뷰 · 프로시저 목록, 각 객체를 읽는/쓰는 위치(`파일:줄`), 관계 → `docs/<모듈명>/ERD.md` 저장. 스키마는 모듈 폴더 밖(`db/mariadb/init/`, `db/mssql/init/`)까지 따라가 읽는다.
5. **비즈니스 규칙 후보** — 조건문 · SQL · 검증 · 매직 값에서 규칙을 뽑아 아래 형식으로 → `docs/<모듈명>/BUSINESS-RULES.md` 저장.
6. **표본 점검 추천** — 사람이 직접 확인할 규칙 3개를 골라 이유와 함께 보고한다(아래 참조).

각 문서 머리말에는 대상, 실제로 읽은 범위(파일 · 줄 범위), 실행한 것이 있으면 그 내용을 사실대로 적는다.

## 규칙 형식
~~~markdown
### BR-01 <한 줄 제목>
- **규칙**: <조건>이면 <결과>한다.
- **근거**: `파일:줄번호`
- **근거 코드**:
  ```<언어>
  <근거 줄 원문 인용 — 요약 · 재작성 금지>
  ```
- **확신도**: 확실(조건문 · SQL · 실행으로 확인) / 추정(이름 · 주석 · 언어 동작으로 짐작)
- **비고**: 주석과 코드 불일치, 매직 넘버, 같은 규칙의 다른 구현 위치, 미확인 사항
~~~
- 주석과 코드가 다른 규칙은 문서 맨 앞 "먼저 볼 것" 표에 올린다.
- 주석에만 있고 코드로 확인되지 않은 내용은 규칙으로 올리지 않고 별도 표에 둔다.

## 하지 말 것 (item-bank 분석에서 실제로 틀렸던 유형)
- **주석을 믿고 동작을 단정하지 않는다.** 주석 "범위 밖 난이도는 대개 0건"을 따랐다가, PHP `(int)` 가 `3a` · `03` · `+3` 을 3 으로 바꿔 난이도 3 문항이 조회됨을 놓쳤다(BR-08). 형변환 · 느슨한 비교 · 콜레이션처럼 언어 · DB 동작에 달린 결과는 실행으로 확인하거나 "추정"으로 표시한다.
- **모듈 폴더 밖이라고 "확인 안 됨"으로 멈추지 않는다.** 코드가 참조하는 뷰 `v_item_public` 의 제외 조건을 스키마 파일에서 읽지 않아 미확인으로 남겼다(CX-10 → BR-01). 뷰 · 프로시저 · 제약은 `db/` 정의까지 따라간다.
- **grep 한 번으로 부재를 단정하지 않는다.** `UPDATE` 로 grep 하면 채번용 `FOR UPDATE` 잠금 절이 걸린다. "수정 기능 없음" 같은 부재 주장은 전체 파일 목록 + 매칭된 줄을 하나씩 읽은 결과를 근거로 쓴다(§3).
- **머리말과 실제 작업을 어긋나게 쓰지 않는다.** "아무것도 실행하지 않았다"고 적은 뒤 실행 확인을 추가해 머리말을 고쳐야 했다. 읽지 않은 줄 범위도 숨기지 않는다.
- 존재하지 않는 함수 · 파일을 인용하지 않는다. 인용 전 해당 줄을 다시 열어 원문과 대조한다.
- 호출 방향(A 가 B 를 부르는지, 그 반대인지)을 이름으로 짐작하지 않는다. 호출 줄을 근거로 댄다.
- 코드에 없는 규칙(기획 의도 · "당연히 그럴 것" 같은 정책)을 만들어 넣지 않는다.

## 마지막 단계: 표본 점검 추천
BUSINESS-RULES.md 저장 후, 사람이 원본 코드와 대조할 규칙 3개를 추천한다.
- 1개는 **가장 그럴듯한(확신도 "확실"이고 뻔해 보이는) 규칙** — 그럴듯해서 검토 없이 넘어가기 쉬운 것.
- 나머지 2개는 주석 · 코드 불일치, "추정" 확신도, 여러 곳에 다르게 구현된 규칙 중에서 고른다.
- 각 추천에 `규칙 ID · 확인할 파일:줄 · 무엇을 보면 판정되는지` 를 적는다.
- 점검 결과 규칙이 바뀌면 BUSINESS-RULES.md 끝 "검증 이력" 표(날짜 · 항목 · 바뀐 내용 · 근거)에 기록한다.
