# 머지 전 검증

검증 대상: $ARGUMENTS

- 위 값이 비어 있으면 `git diff upstream/main...HEAD` 를 검증 대상으로 삼는다.
- 값이 `.patch` 파일 경로이면 `git apply --stat <파일>` 로 변경 목록을 뽑고 patch 본문을 diff 로 읽는다.
- 그 밖의 값(커밋 범위 · 브랜치)은 `git diff <값>` 의 범위로 쓴다.

이 절차는 저장소 루트의 `templates/verification-loop.md` 를 따른다. 판정 항목은 저장소 루트의 `templates/approval-checklist.md` 에 있다. 체크리스트 항목은 이 파일에 옮겨 적지 않으므로 매번 그 파일을 읽는다.

## 원칙

- 코드를 수정하지 않는다(tester 가 추가하는 테스트 파일은 예외). 판정과 수정 방향만 보고한다. 고치기 시작하면 그 순간 "만든 쪽"이 된다.
- 근거 줄번호를 댈 수 없는 지적은 이슈로 올리지 않고 "확인 필요"로 따로 남긴다.
- 테스트를 실행하지 않고 통과했다고 쓰지 않는다.

## 절차

reviewer 또는 tester Sub-agent 가 없는 환경에서는 3 · 4단계를 기존 방식대로 직접 수행한다.

### 1. 요청 범위 확인
- 이 변경으로 무엇을 요청했는지 한 문장으로 확인한다.
- 요청 문장이 주어지지 않았으면 판정하지 않는다. 먼저 질문하고 답을 받은 뒤 2단계로 넘어간다.

### 2. 변경 파일 목록과 diff 읽기
- `git diff --stat <범위>` 로 변경 파일 목록을 먼저 본다(patch 파일이면 `git apply --stat`).
- 파일마다 `git diff <범위> -- <파일>` 로 diff 를 읽는다. 걸린 줄은 필요하면 Read 로 앞뒤를 확인한다.
- 변경 파일을 `modern/api` · `modern/web` · `characterization` · 기타로 나눠 둔다(4단계에서 쓴다).

### 3. 체크리스트 대조
- 직접 하지 않고 reviewer Sub-agent 에 위임한다. 비교 범위(검증 대상)와 1단계의 요청 범위 문장을 그대로 넘긴다.
- reviewer 에게 아래 기준으로 대조하게 한다.
- 저장소 루트의 `templates/approval-checklist.md` 를 읽는다.
- 항목마다 충족 · 미충족 · 확인 필요 중 하나로 표시한다. 심각도(치명 / 경고 / 제안)는 그 파일의 정의를 따른다.
- 컨벤션 항목은 저장소 루트의 `CLAUDE.md` 코딩 컨벤션 · 금지 사항과 대조한다. `convention-check` Skill 이 있으면 그 결과를 쓴다.

### 4. 테스트 실행
직접 하지 않고 tester Sub-agent 에 위임한다. 2단계에서 나눈 변경 폴더와 아래 표를 넘기고, 변경된 폴더의 테스트만 실행하게 한다.
새 로직에 테스트가 없으면 테스트 파일을 추가하게 하고, 실행 결과(명령마다 통과 · 실패 수, 실패한 테스트 이름, 추가한 테스트 파일 목록)를 돌려받는다.

| 변경 폴더 | 실행 위치 | 명령 |
|---|---|---|
| `modern/api` | `modern/api` | `./gradlew test` |
| `modern/web` | `modern/web` | `npm test` |
| 이관 코드 | `characterization` | `npm test` (레거시 대상) 와 `TARGET_BASE_URL=http://localhost:8080 npm test` (새 API 대상) |

- 이관 코드는 레거시 동작을 새 API 로 옮긴 변경을 말한다. 두 명령을 모두 돌린다.
- 서버가 꺼져 있거나 의존성이 설치되지 않아 실행할 수 없으면, 그 사실과 오류 한 줄을 적고 사람에게 기동을 요청한다. 이 경우 "테스트 통과"는 충족으로 표시하지 않는다.
- **사용량 절약:** 대화에는 명령마다 통과 · 실패 수와 실패한 테스트 이름만 남긴다. 전체 로그를 대화에 싣지 않는다. 출력이 길면 파일로 저장한 뒤 요약 줄과 실패 이름만 grep 으로 뽑는다.

### 5. 승인 기준 판정
- reviewer 와 tester 의 보고를 모두 받은 뒤 메인 세션이 네 기준을 최종 판정한다.
- reviewer 와 tester 의 보고가 엇갈리면 엇갈린 지점을 그대로 적고 사람에게 묻는다.
- 네 기준(테스트 통과 / 치명 이슈 0건 / 요청 범위 이탈 없음 / 컨벤션 준수)을 하나씩 판정한다.
- 네 기준이 모두 충족이면 승인, 하나라도 미충족이면 반려.
- 요청 범위를 모르는 상태에서 "요청 범위 이탈 없음"을 충족으로 표시하지 않는다.
- 이슈가 0건이면 경고 · 제안 수준까지 한 번 더 훑은 뒤 확정한다.

## 출력 형식 (순서 고정)

```
판정: 승인 | 반려

| 기준 | 결과 | 근거 |
|---|---|---|
| 테스트 통과 | 충족 / 미충족 | 실행 명령과 통과 · 실패 수, 실패한 테스트 이름 |
| 치명 이슈 0건 | 충족 / 미충족 | 치명 이슈 번호 |
| 요청 범위 이탈 없음 | 충족 / 미충족 | 요청 문장 vs 변경 파일 목록 |
| 컨벤션 준수 | 충족 / 미충족 | 위반 이슈 번호 |

이슈 목록
| # | 심각도 | 파일:줄번호 | 근거 | 수정 방향 |
|---|---|---|---|---|
| 1 | 치명 / 경고 / 제안 | path/to/File.java:42 | ... | ... |

확인 필요
- 파일:줄 또는 항목 — 확인할 내용
```

- 이슈 한 건은 심각도 · 파일:줄번호 · 근거 · 수정 방향 네 칸을 모두 채운다.
- 이슈가 없으면 표 대신 "이슈 없음" 한 줄을 쓴다.

## 하지 말 것

- 코드를 수정하지 않는다(tester 가 추가하는 테스트 파일은 예외).
- 근거 줄번호를 댈 수 없는 지적은 하지 않고 "확인 필요"로 남긴다.
- 테스트를 실행하지 않고 통과했다고 쓰지 않는다.
- 전체 테스트 로그를 대화에 싣지 않는다.
